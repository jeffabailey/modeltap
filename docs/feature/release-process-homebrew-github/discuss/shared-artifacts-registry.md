# Shared Artifacts Registry — release-process-homebrew-github

Single source of truth for every `${variable}` referenced in the journey artifacts. Untracked artifacts are the primary cause of horizontal integration failures — and a release pipeline is **all integration**, end to end.

## Conventions

- **Source of truth** is the canonical producer (a file, a workflow step, or a configuration value).
- **Consumers** are every place the value is read or displayed.
- **Integration risk** is the impact of inconsistency.

## Artifact Table

| Artifact | Source of Truth | Consumers | Integration Risk |
|---|---|---|---|
| `version` | `Cargo.toml [workspace.package].version` | `cargo xtask release-prep` output, `CHANGELOG.md` heading, git tag (with `v` prefix), `release.yml` validate-tag job, release archive filename, GitHub Release title, Homebrew formula `version` field, `modeltap --version` stdout (via clap `CARGO_PKG_VERSION` at compile time) | **CRITICAL** — drift between any two consumers ships a release that lies about its identity. The validate-tag job is the primary guard. |
| `tag` | `git tag` (string format: `v` + `${version}`) | `release.yml` workflow trigger filter (`tags: v*.*.*`), validate-tag job assertion, GitHub Release page URL, release archive download URL embedded in formula | **CRITICAL** — workflow triggers, URL stability, and tap-bump correctness all depend on tag exactly equaling `v` + version. |
| `changelog` | `CHANGELOG.md` (generated by `git-cliff` from conventional commits between previous tag and HEAD) | Maintainer prep PR description, GitHub Release notes (extracted by `[${version}]` section), README "What's new" link | **HIGH** — drift means the GitHub Release notes contradict the changelog file in the repo. |
| `binary-targets[]` | `release.yml` build job `matrix.target` list (4 entries: aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu) | Build job matrix, Homebrew formula `on_macos`/`on_linux` blocks, README install matrix table | **HIGH** — adding/removing a target requires updating release.yml AND the formula template AND the README. |
| `archive-name` | `release.yml` build job env: `modeltap-${version}-${target}.tar.gz` | Build job tar step, GitHub Release upload step, Homebrew formula `url` field per target | **HIGH** — typo in any consumer breaks `brew install` with a 404. |
| `sha256[target]` | `release.yml` build job: `sha256sum ${archive} > ${archive}.sha256` (one per target) | GitHub Release attached `.sha256` file per archive, `bump-tap-formula` job (read from artifact, never recomputed), Homebrew formula `sha256` field per platform block | **CRITICAL** — sha256 mismatch causes `brew install` to fail with "SHA256 mismatch". The bump job MUST read from the `.sha256` artifact, not rehash. |
| `release-url[target]` | Template: `https://github.com/jeffabailey/modeltap/releases/download/${tag}/${archive-name}` | GitHub Release attachment URL, Homebrew formula `url` field per platform block, README direct-download fallback links | **CRITICAL** — both the GitHub upload and the formula MUST be derived from the same template. Hand-typing in either location is a smell. |
| `tap-name` | The tap repo name itself: `jeffabailey/homebrew-modeltap` | README install instructions (`brew tap ${tap-name}`), `release.yml` `bump-tap-formula` job target repo, the end-user's `brew tap` command | **HIGH** — renaming the tap (e.g., on a future move to a `modeltap` GitHub org) breaks every existing user's `brew tap` line. Treat as a one-way decision. |
| `formula-content` | Rendered by `release.yml` `bump-tap-formula` job from a template, using `${version}`, `${release-url[*]}`, `${sha256[*]}` | The single file `Formula/modeltap.rb` in the tap repo, consumed by `brew install` and `brew test-bot` | **CRITICAL** — this IS the user-facing release artifact for Homebrew users. |
| `install-command` | README install section, derived from `${tap-name}` + binary name | README, GitHub Release notes "Install with" block, modeltap-tui repo description (if separate), social posts | **MEDIUM** — drift means users follow stale install instructions; mostly self-correcting (brew tells them what's wrong). |
| `release-runbook` | `RELEASING.md` at repo root | Maintainer reference, contributor onboarding | **LOW** — a stale runbook is annoying but not destructive; the workflow file is the source of truth for what actually happens. |
| `tap-bump-token` | A GitHub fine-grained PAT or deploy key with `Contents: Read+Write` and `Pull Requests: Read+Write` on `jeffabailey/homebrew-modeltap`, stored as `GH_TAP_TOKEN` in the modeltap repo's Actions secrets | `release.yml` `bump-tap-formula` job authentication | **HIGH** — token expiry silently breaks the tap bump until rotated. DEVOPS to add monitoring. |
| `slsa-attestation` | `actions/attest-build-provenance@v2` output per archive (signed by GitHub's OIDC provider) | GitHub Release attachment (sigstore bundle), `gh attestation verify` for end users who care about supply chain | **MEDIUM** — missing attestation does not break install but degrades the supply-chain story. |
| `ci-parity-gates` | `release.yml` build job steps: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --locked` | Build job (must pass before any release artifact is built); MUST mirror `.github/workflows/ci.yml` exactly | **HIGH** — drift between ci.yml and release.yml means a release could ship code that ci.yml would have rejected. Both files reference the same toolchain pinning conventions. |
| `cli-vocabulary` | `journey-tag-to-brew-install-visual.md` (vocabulary table) | Every maintainer-facing message, README, RELEASING.md, workflow job names, error messages | **MEDIUM** — terminology drift makes the workflow harder for contributors to read. |

## Open Source-of-Truth Decisions (DESIGN must close)

| ID | Artifact | Open question | Default proposed |
|---|---|---|---|
| D1 | `tap-name` | Personal namespace (`jeffabailey/homebrew-modeltap`) vs future `modeltap` GitHub org | Personal namespace for v1; revisit on org migration. Treat as one-way decision; document migration path. |
| D2 | Release-cut trigger | Manual `git tag` push vs `release-please` PR vs `cargo-release` | Manual `git tag` push for v1 (simplest, least magic). |
| D3 | `slsa-attestation` | Required vs optional in v1 | Required — `actions/attest-build-provenance@v2` adds ~30s per build, no maintainer toil. |
| D4 | `binary-targets[]` | Just `modeltap` (TUI) vs `modeltap` + `modeltap-cli` | Just `modeltap` for v1. `modeltap-cli` ships through the same pipeline if/when it exists. |
| D5 | `changelog` source | Hand-curated vs `git-cliff` vs `release-please` derived | `git-cliff` driven by conventional commits (already in use per recent commit history). |
| D6 | macOS code signing/notarization | Skip vs `rcodesign` vs Apple Developer ID + notarization | Skip for v1; document `xattr` workaround in README; track as a future feature. |
| D7 | `tap-bump-token` | Deploy key (per-repo SSH key) vs fine-grained PAT vs GitHub App | Fine-grained PAT for v1 (simplest). Migrate to GitHub App if multiple maintainers join. |

## Validation Plan (during DESIGN review)

1. Every `${variable}` in `journey-tag-to-brew-install-visual.md` MUST appear in this table.
2. Every consumer of an artifact MUST read from the source of truth, not a hardcoded literal. Specifically:
   - `release.yml` MUST NOT hardcode `${version}` — it derives from the tag.
   - `Formula/modeltap.rb` MUST NOT hardcode `${sha256[*]}` — `bump-tap-formula` reads each from the corresponding `.sha256` artifact file.
   - `README.md` install snippet MUST be checked at release time against the actual `${tap-name}`.
3. Cross-step appearances of the same artifact (e.g., `${version}` in steps 1, 2, 3, 4, 5) MUST resolve to identical strings — verified by the validate-tag job and by the formula's `test do` block running `modeltap --version`.
4. Open decisions D1-D7 MUST be closed (defaults accepted or alternatives chosen) before DESIGN begins.

## Integration Checkpoints (cross-step invariants)

| Invariant | Steps involved | Failure mode |
|---|---|---|
| `${tag}` == `"v" + ${version}` | 2 (tag push) → 3 (validate-tag job) | Tag points at wrong code; entire release lies about its identity |
| For each target T: GitHub Release `.sha256` content == Homebrew formula `sha256` field for T | 3 (publish) → 4 (tap bump) | `brew install` fails with "SHA256 mismatch" for the user |
| For each target T: GitHub Release URL for `${archive-name[T]}` == Homebrew formula `url` field for T | 3 (publish) → 4 (tap bump) | `brew install` fails with 404 |
| `${version}` (Cargo.toml) == `modeltap --version` stdout | 1 (prep) → 5 (user verifies) | Binary lies about its own version — root cause is usually a stale build cache |
| `bump-tap-formula` runs ONLY if `publish-github-release` succeeded | 3 → 4 | Tap PR points at non-existent GitHub Release URLs |
| `publish-github-release` runs ONLY if ALL `build` matrix cells succeeded | 3 (build) → 3 (publish) | Half-published release: some platforms work, others 404 |
| `release.yml` runs CI parity gates (fmt, clippy, test) BEFORE any `cargo build --release` | within step 3 | A release ships code that ci.yml would have rejected |

## Cross-Repo Coordination

This is the only modeltap feature whose pipeline crosses repository boundaries. Two repos are involved:

| Repo | Role | Owner |
|---|---|---|
| `jeffabailey/modeltap` (this repo) | Source code, `release.yml`, generates artifacts, opens tap PR | Maintainer |
| `jeffabailey/homebrew-modeltap` (separate) | `Formula/modeltap.rb`, brew test-bot, end-user install target | Maintainer |

Cross-repo authentication is handled by `${tap-bump-token}`. The tap repo MUST contain only:
- `Formula/modeltap.rb` (auto-rewritten by `bump-tap-formula`)
- `README.md` (hand-maintained, points users back to the main repo)
- `.github/workflows/test-bot.yml` (runs `brew test-bot` on PRs)

Anything else in the tap repo is a smell; the tap is a thin manifest, not a project.
