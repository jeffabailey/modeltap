# Release Strategy — modeltap-tui

**Tool:** `cargo-dist` (per ADR-011)
**Versioning:** SemVer (plugin trait stability is the SemVer contract)
**Cadence:** as-needed; no time-boxed releases

## 1. Release Targets

Per architecture-design §10:

| Target triple | Use |
|---|---|
| `x86_64-apple-darwin` | macOS Intel |
| `aarch64-apple-darwin` | macOS Apple Silicon |
| `x86_64-unknown-linux-gnu` | Linux x86_64 (also serves WSL users) |
| `aarch64-unknown-linux-gnu` | Linux ARM (e.g., Raspberry Pi 5, Ampere) |

Native Windows is **not** a release target (per C2). The native Windows binary, if built, refuses to run with a clear message pointing to WSL. WSL users install the Linux x86_64 build.

`musl` static-linked Linux build is **deferred** to v1.x. The `gnu` build covers most Linux users; musl matters only for niche distros (Alpine) — community-driven post-v1.

## 2. cargo-dist Configuration

In root `Cargo.toml`:

```toml
[workspace.metadata.dist]
cargo-dist-version = "0.21.0"  # pin
ci = ["github"]
installers = ["shell", "powershell", "homebrew"]
tap = "<org>/homebrew-modeltap"
formula = "modeltap"
targets = [
    "x86_64-apple-darwin",
    "aarch64-apple-darwin",
    "x86_64-unknown-linux-gnu",
    "aarch64-unknown-linux-gnu",
]
pr-run-mode = "plan"
allow-dirty = ["ci"]
include = ["LICENSE", "README.md", "CHANGELOG.md"]

# Checksums for tamper detection
checksum = "sha256"
```

`cargo dist init` then `cargo dist generate` writes `.github/workflows/release.yml`. Do not hand-edit; regenerate after config changes.

The shell installer (`installer.sh`) and PowerShell installer (`installer.ps1`) are auto-generated — useful for one-liner installs from GitHub Releases.

## 3. Release Trigger

Tag-push to GitHub triggers the release workflow:

```bash
# Maintainer flow
git checkout main
git pull
# bump version in Cargo.toml; update CHANGELOG.md
cargo workspaces version --no-git-commit  # or hand-edit
git add Cargo.toml CHANGELOG.md
git commit -m "chore: release v1.0.0"
git tag v1.0.0
git push origin main v1.0.0
```

Tag pattern: `v<MAJOR>.<MINOR>.<PATCH>`. Pre-releases use `v1.0.0-rc.1`, `v1.0.0-beta.1`, etc.

The release workflow:
1. Builds on native macOS + Linux runners (cross-compile for ARM via cargo-zigbuild or runner architecture)
2. Strips debug symbols
3. Tarballs each binary with LICENSE and README
4. Generates SHA256SUMS file
5. Creates GitHub Release with all artifacts
6. Updates Homebrew formula in tap repo
7. (Optional) Publishes to crates.io

## 4. SemVer Contract

The `Tool` trait in `modeltap-core` is the public extensibility API. SemVer is interpreted strictly:

| Change | Bump |
|---|---|
| Add a new method to `Tool` with default implementation | MINOR |
| Add a new method without default impl | MAJOR (breaks every plugin) |
| Change a method signature (params, return types) | MAJOR |
| Add a variant to a public algebraic type with `#[non_exhaustive]` | MINOR |
| Add a variant without `#[non_exhaustive]` | MAJOR |
| Bug fix (no API change) | PATCH |
| New plugin under `plugins/` (does not change `Tool`) | MINOR |
| New TUI feature (does not change `Tool`) | MINOR |
| Breaking change to `~/.modeltap/launch.log` JSONL schema | MINOR (consumer is local; document in CHANGELOG) |
| Breaking change to `~/.modeltap/config.toml` schema | MAJOR (user-edited file) |

Recommendation: derive `#[non_exhaustive]` on all public enums in `modeltap-core` from day one to keep room for additive evolution.

`cargo semver-checks` (optional CI job) can mechanically detect SemVer violations against the previous published crate version. Defer to v1.x; for v1.0.0 manual review by maintainer is sufficient.

## 5. Distribution Channels

### 5.1 GitHub Releases (canonical)

- Tarballs per target: `modeltap-v1.0.0-x86_64-apple-darwin.tar.xz`
- `SHA256SUMS` and (optionally) `SHA256SUMS.sig` if signing is added later
- Source tarball auto-generated by GitHub
- `installer.sh` and `installer.ps1` for one-liner install:
  ```bash
  curl --proto '=https' --tlsv1.2 -sSf https://github.com/<org>/modeltap/releases/download/v1.0.0/modeltap-installer.sh | sh
  ```

### 5.2 Homebrew Tap (`<org>/homebrew-modeltap`)

cargo-dist auto-publishes a formula to the tap repo on each release. User flow:

```bash
brew tap <org>/modeltap
brew install modeltap
```

Submission to homebrew-core is **deferred** — requires manual review, version stability proof, and an active maintainer. Tap is sufficient for v1 and Devon persona.

### 5.3 crates.io (`cargo install modeltap`)

Publish `modeltap` (the binary crate inside `crates/modeltap-app`) to crates.io. Rust-aware users can install with:

```bash
cargo install modeltap
```

Requires:
- All workspace member crates published (or `[package]` in `modeltap-app` references workspace deps with explicit versions)
- API token in GitHub repo secrets (`CARGO_REGISTRY_TOKEN`)

cargo-dist supports `publish-jobs = ["homebrew", "cargo:..."]` style configuration.

### 5.4 Deferred channels

| Channel | Why deferred |
|---|---|
| AUR (`modeltap-bin`, `modeltap`) | Community-driven; submit only after stable user base |
| Nix (`pkgs.modeltap`) | Same; Nix maintainers have strict review process |
| `.deb` / `.rpm` | Niche users; cargo-dist supports via `[workspace.metadata.dist] formats = ["deb", "rpm"]` if needed in v1.x |
| Snap / Flatpak | Sandboxing complicates `~/.ollama` access; defer |
| MacPorts | Niche; community |

## 6. Code Signing (Deferred)

v1 ships unsigned. macOS users may see a Gatekeeper warning ("modeltap can't be opened because the developer cannot be verified"). INSTALL.md documents the workaround:

```bash
xattr -d com.apple.quarantine /usr/local/bin/modeltap  # or wherever brew installed
```

Apple Developer ID code signing is deferred:
- Cost: $99/year Apple Developer Program enrollment
- Setup complexity: certificate management, notarization API
- Not blocking for an OSS dev-tool whose users are technical

Linux: no code signing convention; not applicable.

If the project gains popularity and the Gatekeeper friction becomes a complaint, revisit in v1.x. Apple Notary Service support is a one-line cargo-dist addition.

## 7. Reproducibility

Releases are reproducible from the tag:

- `Cargo.lock` is committed and used in CI (`--locked` everywhere)
- Pinned `cargo-dist-version` in workspace metadata
- Pinned GitHub Actions versions (e.g., `dtolnay/rust-toolchain@stable` resolves to a specific Rust version per the action's behavior; for stricter reproducibility, pin to `@1.84.0` or similar)
- No build-time network access beyond crates.io (verified by `cargo deny check sources`)
- `RUSTC_BOOTSTRAP=0` (default); no nightly features

Bit-for-bit reproducible builds are not guaranteed (Rust + LLVM produce minor non-determinism in object files). Reproducibility goal here is "anyone can build the same source from the tag and get a working binary," not "byte-identical artifact."

## 8. Release Process (the runbook for RELEASE.md)

```markdown
# RELEASE.md — How to cut a release

1. Ensure `main` is green: visit Actions tab, confirm last commit's CI is fully green on macOS + Linux.
2. Update `Cargo.toml` versions across the workspace. For a uniform bump, use:
   ```bash
   cargo install cargo-workspaces  # one time
   cargo workspaces version --no-git-commit minor  # or major / patch
   ```
3. Update `CHANGELOG.md` with the new section. Use Keep a Changelog format.
4. Commit:
   ```bash
   git add Cargo.toml Cargo.lock CHANGELOG.md
   git commit -m "chore: release v$(grep '^version' Cargo.toml | head -1 | cut -d'"' -f2)"
   ```
5. Tag and push:
   ```bash
   VERSION=$(grep '^version' Cargo.toml | head -1 | cut -d'"' -f2)
   git tag "v$VERSION"
   git push origin main "v$VERSION"
   ```
6. Watch the release workflow in the Actions tab. On success:
   - GitHub Release created with all artifacts
   - Homebrew tap repo updated
   - (If configured) crates.io publish completed
7. Smoke test:
   ```bash
   brew update
   brew upgrade modeltap   # or brew install
   modeltap --version       # expect "modeltap $VERSION"
   modeltap                 # launches; verify your local Ollama models appear
   ```
8. Update README.md installation section if version-pinned anywhere.
9. Announce in CHANGELOG.md and (optionally) social channels.

## Hotfix flow

For an urgent fix (e.g., data-loss bug):
1. Create branch `hotfix/v1.0.1` from the v1.0.0 tag.
2. Apply minimal fix; bump PATCH; CHANGELOG entry.
3. PR back to main; merge.
4. Tag `v1.0.1` and push.
```

## 9. CHANGELOG.md Format

Keep a Changelog 1.1.0 format. Sections per release:

```markdown
## [1.0.0] - 2026-XX-XX

### Added
- ...

### Changed
- ...

### Deprecated
- ...

### Removed
- ...

### Fixed
- ...

### Security
- ...
```

Generated commit messages from `git log v0.x..HEAD --pretty=format:'- %s'` are a starting point; maintainer curates into the categories above.

## 10. Pre-1.0 Strategy

Before v1.0.0 is tagged:

- Walking skeleton (US-01..US-06) lives on `main` with no release tags
- Release 1 (US-04, US-07, US-09, US-12, US-13, US-15, US-16) — optional `v0.1.0-alpha` tag
- Release 2 (US-08, US-10, US-11, US-14, US-17, US-19) — optional `v0.2.0-beta` tag
- Release 3 (US-18, US-20) — `v1.0.0` candidate

Pre-1.0 SemVer is permissive: any release may break anything. Document this in README. Once v1.0.0 ships, the trait is locked under SemVer.

## 11. Rollback Strategy (such as it is)

For an installed-binary tool, rollback = "user reinstalls the previous version." There is nothing to roll back on the publisher side.

That said, defensive measures:

- **GitHub Releases preserves all historical tags** — users can always download v0.x even after v1.x ships
- **Homebrew formula history** — `brew install modeltap@1.0.0` after a tap revision (cargo-dist supports versioned formulae)
- **Yank a bad release on crates.io** — `cargo yank --version 1.0.0` prevents new installs but does not remove the version from people who installed it

For a serious bug (data-loss class):
1. Cut a hotfix release (v1.0.1) within 24 hours
2. Update the GitHub Release notes for v1.0.0 with a prominent warning and link to v1.0.1
3. Yank v1.0.0 on crates.io if it was published there
4. Open a tracking issue tagged `accidental-loss` (per K5 measurement)

K5 (zero accidental-loss reports in 90 days) is the success measure that this rollback runbook should never need to execute.

## 12. Release Quality Gates (pre-tag)

Before pushing a tag, verify:

- [ ] All items in `production-readiness-checklist.md` are green
- [ ] CHANGELOG.md has a section for the new version
- [ ] No open issues with the `release-blocker` label
- [ ] cargo-deny passes on the tagged commit
- [ ] `cargo dist plan` shows the expected artifact set

These are operator-side gates (maintainer responsibility), not CI gates (CI cannot self-gate a release tag without invoking the release workflow).
