# ADR-011: Release Tooling — `cargo-dist`

## Status

Accepted (2026-04-28).

## Context

modeltap ships as a single Rust binary for 4 targets (x86_64-darwin, aarch64-darwin, x86_64-linux-gnu, aarch64-linux-gnu) via:

- GitHub Releases (canonical tarballs + checksums)
- Homebrew tap (macOS users — Devon persona)
- crates.io (`cargo install modeltap`)

We need release tooling that:

- Cross-builds for 4 targets from GitHub Actions hosted runners
- Generates a GitHub Release with all artifacts attached
- Generates and updates a Homebrew formula in a tap repo
- Computes SHA256 checksums
- Is reproducible from a tag push (no manual steps after `git push --tags`)
- Is itself maintained and stable (the release path is critical infrastructure)

## Decision

**Use `cargo-dist`** (axodotdev/cargo-dist). Configuration lives in `[workspace.metadata.dist]` of the root `Cargo.toml`. The release workflow at `.github/workflows/release.yml` is generated by `cargo dist generate` and committed to the repo (not regenerated at build time — change-control hygiene).

## Alternatives considered

### Alternative A — `goreleaser` (cross-language)

**Pros:** mature, language-agnostic (could ship a future Go-based companion tool from the same pipeline).

**Cons:** Go-centric ergonomics; less idiomatic for a Rust workspace; doesn't read from `Cargo.toml`; community-maintained Rust support is thinner than cargo-dist's first-party support; an extra non-Rust toolchain on the developer machine. **Rejected on Rust-native preference.**

### Alternative B — Hand-rolled GitHub Actions workflow

**Pros:** no external tool dependency; total control over every step.

**Cons:** maintenance burden — cross-compilation matrix, sccache wiring, tarball assembly, SHA256 generation, GitHub Release API, Homebrew formula templating — all hand-coded. Easy to break, hard to test. Reinvents what cargo-dist does. **Rejected as YAGNI / not-invented-here.**

### Alternative C — `cross` + custom shell scripts

**Pros:** `cross` solves Linux cross-compilation cleanly (containerized cross targets).

**Cons:** still needs the orchestration layer that cargo-dist provides. Becomes a hand-rolled workflow with `cross` inside it. **Rejected on completeness.**

### Alternative D (CHOSEN) — `cargo-dist`

Rust-native, Cargo-integrated, generates the GHA workflow, supports all our targets, supports Homebrew tap auto-publish, supports installer scripts, computes checksums, well-maintained by axodotdev (active 2024-2026).

## Alternatives explicitly NOT considered

- **`cargo-release`** — version bumping and crate publishing only; doesn't build binaries or distribute. Complementary to cargo-dist (can use `cargo-release` for crates.io publish step), not a substitute.
- **Native cargo-only flow** — `cargo publish` is fine for crates.io but doesn't address GitHub Releases or Homebrew. Insufficient alone.

## Consequences

### Positive

- One-command release: bump version → tag → push. Workflow does the rest.
- All 4 platform builds parallelize across runners; total release time ~10-15 min.
- Homebrew formula stays in lockstep with releases automatically — one less thing for maintainer to forget.
- Installer scripts (`installer.sh`, `installer.ps1`) are generated for free — useful for `curl | sh` style installs documented in INSTALL.md.
- Configuration in `Cargo.toml` is version-controlled and reviewable; no separate config dance.
- cargo-dist supports MSI / DEB / RPM additively if v1.x wants them — no rework needed.

### Negative

- External dep on cargo-dist itself. Pinned via `cargo-dist-version = "0.21.0"` (or whatever current at adoption time) to prevent silent behavior changes.
- The generated `release.yml` is opaque — debugging release failures requires reading 200+ lines of generated YAML. Mitigation: maintainer runs `cargo dist plan` locally to validate config before pushing tags.
- Code signing (macOS Apple Developer ID) is supported by cargo-dist but adds setup cost; deferred to v1.x per `release-strategy.md` §6.

### Neutral

- The release workflow runs only on tag push (`v*` pattern). Tag deletion does not delete the GitHub Release — manual cleanup if a tag is yanked. Acceptable.
- Pre-1.0 tags (`v0.1.0-alpha`, etc.) work the same way; cargo-dist marks pre-releases on GitHub automatically based on the SemVer pre-release suffix.

## Enforcement

- Root `Cargo.toml` `[workspace.metadata.dist]` per `release-strategy.md` §2.
- `.github/workflows/release.yml` regenerated only by `cargo dist generate`; reviewed in PR.
- Maintainer follows `RELEASE.md` (in repo root, authored in DELIVER) for the 9-step release flow.
- Production-readiness checklist requires a successful `cargo dist plan` and a successful pre-1.0 dry-run release before v1.0.0 tag.
